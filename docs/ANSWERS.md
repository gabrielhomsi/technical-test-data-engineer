# Réponses du test

## _Utilisation de la solution (étape 1 à 3)_

- Move to project root folder
- Create a virtual environment, such as `python -m virtualenv venv`
- Activate the virtual environment: `source venv/bin/activate`
- Install dependencies: `pip install -r requirements.txt`
- Run tests with `python -m pytest`
- Run the pipeline: `python src/pipelines/ingestion_pipeline.py`
- Check extracted data in `tracks.json`, `users.json` and `listen_history.json`
- Check log in `ingestion_pipeline.log`

## Questions (étapes 4 à 7)

### Étape 4

Because of the relational structure of the data, I would use a relational database such as PostgreSQL.
To represent the list of tracks listened by a user, I would create a `listen_history` table with a composite primary key,
linking each row of that table to a single user-track pair. To list all tracks for a given user, a select query that
joins tables `listen_history` and `tracks` can be used. The three tables are described below:

#### Tracks table

- Primary key: id
- Other fields
    - name
    - artist
    - songwriters
    - duration
    - genres
    - album
    - created_at
    - updated_at

#### Users table

- Primary key: id
- Other fields
    - first_name
    - last_name
    - email
    - gender
    - favorite_genres
    - created_at
    - updated_at

#### Listen history table

- Composite primary key = (user_id, track_id)
- Foreign keys
    - user_id, references users table, id column
    - track_id, references tracks table, id column
- Other fields
    - created_at
    - updated_at

### Étape 5

- Inspect/monitor logs generated by the pipeline (file `ingestion_pipeline.log`)
- Use a pipeline orchestration tool such as Airflow to run the pipelines
    - Some execution metrics are automatically monitored by Airflow, and alerting can be configured
- Alternatively, a more fine-grained solution is to use a stack such as ELK (Elasticsearch, Logstash and Kibana) to
  collect and display logs/metrics
- Key metrics are:
    - date and time that pipeline started execution
    - total time to execute pipeline & deviation from average execution time
    - status of pipeline execution (finished successfuly, failed, etc)
    - number of tracks, users and listen_history records that pipeline added to database
- Bonus: add a /health endpoint to the API, monitor it with a tool like Prometheus and set up alerting for important
  events (example, API is down)

### Étape 6

After extracting data from the API, trigger or schedule the execution of a `generate_recommendations` pipeline for each
user. For a given user, such pipeline should only be triggered if the ingestion pipeline collected new listening data
for that particular user. If the user has not listened to anything new since the last time the ingestion pipeline has
executed, then there is no need to generate new recommendations.

Additionally, the `generate_recommendations` pipeline may be triggered for all users after the recommendation model is
retrained.

### Étape 7

The retraining of the recommendation model should be triggered only after the listen history data is significantly
different from the data used to train the last version of the model. Below are the high level steps of the retrain_model
pipeline:
- Load listen history data
- Check if data significantly changed since last model training
- If yes, retrain model, otherwise stop pipeline execution
- Compare performance with previous model
- Pick best model and deploy
- Potentially trigger `generate_recommendations` pipeline
